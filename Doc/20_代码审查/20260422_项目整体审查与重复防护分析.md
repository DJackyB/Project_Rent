# 项目整体审查与重复防护分析

**审查日期**：2026-04-22  
**审查范围**：`Assets/Scripts`、`Assets/Tests`、`Doc`、Unity Console 当前告警  
**审查方式**：静态代码阅读 + 文档对照 + 控制台抽样  
**说明**：本次仅记录发现，未修改业务代码。当前工作区已有用户改动：`Assets/Scripts/Runtime/UI/Settlement/UISettlementSequenceController.cs`。

---

## 一、总体结论

项目已经从早期“缺少校验/缺少保护”的阶段，演进到“保护很多、保底很多”的阶段。

当前主要风险不再是完全没有防护，而是：

1. 防护逻辑分散在 UI、流程、效果、数据导入、启动校验多个层级。
2. 一些临时状态通过全局上下文传递，生命周期不够清晰。
3. 多个模块针对同一类风险各自补了一层保护，短期安全，长期容易造成状态来源分裂。
4. `TurnManager` 承载过多职责，奖励、商店、结算、出牌、动画等待都混在同一个类中。

整体方向建议是：先修真正会导致错误的状态和空引用问题，再逐步收敛重复防护，最后做结构拆分。

## 二、高优先级风险

### 1. 随机事件执行卡牌效果时可能空引用

**相关文件**

- `Assets/Scripts/Runtime/GameFlow/RandomEventEffectBridge.cs`
- `Assets/Scripts/Runtime/Card/CardEffectFactory.cs`
- `Assets/Scripts/Runtime/Card/Effects/AddMoneyEffect.cs`
- `Assets/Scripts/Runtime/Card/Effects/ReduceMoneyEffect.cs`
- `Assets/Scripts/Runtime/Card/Effects/AddMoneyByEmptyRoomsEffect.cs`
- `Assets/Scripts/Runtime/Card/Effects/AddMoneyByRoomCountEffect.cs`

**现象**

`RandomEventEffectBridge.OnOptionSelected(...)` 会通过：

```csharp
CardEffectFactory.Execute(option.effect, context);
```

执行随机事件选项中的效果字符串。

而 `CardEffectFactory.Execute(...)` 内部会以 `source = null` 执行：

```csharp
effect?.Execute(null, context);
```

但多个效果类仍然直接访问：

```csharp
source.Data.cardName
```

例如：

- `AddMoneyEffect`
- `ReduceMoneyEffect`
- `AddMoneyByEmptyRoomsEffect`
- `AddMoneyByRoomCountEffect`

**风险**

如果随机事件复用这些普通卡牌效果，会触发 `NullReferenceException`。这类问题在普通出牌流程中不明显，因为普通卡牌执行时 `source` 通常存在。

**建议**

新增统一 helper，例如：

```csharp
private static string EffectSourceName(CardInstance source)
{
    return source != null && source.Data != null ? source.Data.cardName : "Unknown";
}
```

或者放到公共工具中，所有效果日志和捕获标签统一走 helper。

优先替换所有直接 `source.Data` 的效果类。

### 2. `EffectContext.SelectedRoom` 是共享临时状态，出牌后没有恢复

**相关文件**

- `Assets/Scripts/Runtime/GameFlow/TurnManager.cs`
- `Assets/Scripts/Runtime/Card/ICardEffect.cs`
- `Assets/Scripts/Runtime/GameFlow/RandomEventEffectBridge.cs`

**现象**

`TurnManager.PlayCard(...)` 中会写入全局 `GameContext`：

```csharp
context.EffectContext.SelectedRoom = targetRoom;
```

随后执行即时效果。但执行结束后没有清理或恢复旧值。

随机事件选项执行时复用的是：

```csharp
GameManager.Instance?.GameContext
```

因此依赖 `SelectedRoom` 的效果可能读到上一次出牌留下的房间目标。

**风险**

某些本应“无房间上下文”的效果可能误作用到旧房间。尤其是随机事件、全局效果、后续新增效果会比较危险。

**建议**

把 `SelectedRoom` 改成作用域状态。

最低成本做法：

```csharp
var previousRoom = context.EffectContext.SelectedRoom;
context.EffectContext.SelectedRoom = targetRoom;
try
{
    // Execute effects.
}
finally
{
    context.EffectContext.SelectedRoom = previousRoom;
}
```

更理想的方式是做一个 `EffectExecutionScope`，同时管理：

- `SelectedRoom`
- `SettlementCapture`
- `IsExtraRoomSettlementActive`

### 3. 0 费用卡会产生误导性 warning

**相关文件**

- `Assets/Scripts/Runtime/GameFlow/TurnManager.cs`
- `Assets/Scripts/Runtime/Economy/MoneyManager.cs`

**现象**

Unity Console 当前存在告警：

```text
[MoneyManager] ReduceMoney received non-positive amount: 0
```

原因是 `TurnManager.ResolveCardAfterPlay(...)` 无论费用是否为 0，都会调用：

```csharp
MoneyManager.Instance.ReduceMoney(card.Data.cost)
```

而 `MoneyManager.ReduceMoney(0)` 会打印 warning 并返回 true。

**风险**

0 费用卡是正常设计，不应污染控制台。长期会让真正的 warning 被淹没。

**建议**

两种方式任选其一：

1. 在 `TurnManager` 中仅当 `cost > 0` 时扣费。
2. 在 `MoneyManager.ReduceMoney(0)` 中直接返回 true，不记录 warning；负数仍记录 warning。

推荐第二种，因为 `ReduceMoney(0)` 从语义上可以视为 no-op 成功。

### 4. 效果参数解析仍然偏散

**相关文件**

- `Assets/Scripts/Runtime/Card/CardEffectFactory.cs`
- `Assets/Scripts/Runtime/Card/CardEffectRegistration.cs`

**现象**

`CardEffectFactory.Register(effectId, expectedArgCount, factory)` 只检查参数数量下限。具体解析集中在注册处：

```csharp
int.Parse(args[0])
float.Parse(args[1], CultureInfo.InvariantCulture)
Enum.Parse(...)
```

这会带来几个问题：

- 空白参数靠 parse 异常暴露。
- 多余参数没有统一策略。
- 范围限制散在效果构造或运行逻辑里。
- 错误信息依赖异常文本，不够策划友好。

**建议**

引入 `EffectArgs` 或类似工具：

```csharp
EffectArgs.RequireInt(args, 0, "amount");
EffectArgs.RequireFloat(args, 1, "multiplier", min: 0f);
EffectArgs.RequireEnum<TagType>(args, 0, "tag");
EffectArgs.RequireExactCount(args, 2);
```

让启动校验、导表校验、运行时解析的错误信息一致。

## 三、重复防护与冗余点

### 1. 拖拽取消和 Tooltip 隐藏重复出现

**相关文件**

- `Assets/Scripts/Runtime/UI/UIManager.cs`
- `Assets/Scripts/Runtime/UI/UICardDragController.cs`

**现象**

`UIManager` 在多个事件入口中重复执行：

```csharp
cardDragController?.CancelCurrentDrag(true);
TooltipServices.Current.HideAll();
```

包括：

- 阶段切换
- 卡牌打出
- 回合开始
- 游戏结束
- `RefreshAll`

**判断**

这些防护本身合理，因为 UI 交互状态确实应该在阶段变化时清理。但重复散落会让后续维护不方便。

**建议**

抽成一个私有方法：

```csharp
private void ResetTransientInteraction()
{
    cardDragController?.CancelCurrentDrag(true);
    TooltipServices.Current.HideAll();
}
```

这样后续如果还要清理 hover、popup、pointer capture，只需改一处。

---

### 2. 奖励/商店 UI 引用校验重复

**相关文件**

- `Assets/Scripts/Runtime/UI/UIManager.cs`
- `Assets/Scripts/Runtime/GameFlow/TurnManager.cs`

**现象**

`UIManager.Start()` 中已经通过 `ValidateRequiredSceneReferences()` 校验 `_cardRewardPanel` 和 `_cardShopPanel`。

但事件触发时仍然再次抛异常：

```csharp
if (_cardRewardPanel == null)
{
    throw new InvalidOperationException(...);
}
```

`TurnManager` 在奖励和商店流程中也会检查 `UIManager.Instance == null` 并抛异常。

**判断**

主流程 UI 必填是对的；但同类异常分散在多个位置，维护成本偏高。

**建议**

保留启动校验作为主防线。事件入口可以改成：

- 复用统一 `EnsureRewardPanel()` / `EnsureShopPanel()`。
- 或记录错误并返回，避免同一问题在多个调用点用不同文案抛出。

---

### 3. 拖拽验证和正式出牌验证是重复但必要

**相关文件**

- `Assets/Scripts/Runtime/UI/UICardDragController.cs`
- `Assets/Scripts/Runtime/GameFlow/TurnManager.cs`

**现象**

拖拽过程中 `UICardDragController.TryResolveValidDropZone(...)` 会调用 `TurnManager.ValidatePlay(...)`。

动画完成后 `CommitPlay(...)` 再调用 `TurnManager.PlayCard(...)`，而 `PlayCard(...)` 内部又调用 `ValidatePlay(...)`。

**判断**

这层重复不能直接删除。因为拖拽验证和实际提交之间有动画时间，金钱、阶段、卡牌状态都可能变化。

**建议**

保留双重验证，但可以让失败路径更清晰：

- UI 验证只用于高亮和提示。
- 提交验证是权威结果。
- 若两次结果不同，Debug 模式下记录一次状态变化，方便排查“拖上去合法，松手后失败”的边界问题。

---

### 4. 额外结算防递归有硬编码痕迹

**相关文件**

- `Assets/Scripts/Runtime/Card/Effects/TriggerSelectedRoomSettleEffect.cs`
- `Assets/Scripts/Runtime/Card/Effects/TriggerSettleRoomsWithAffixEffect.cs`
- `Assets/Scripts/Runtime/Card/ICardEffect.cs`

**现象**

两个额外结算效果都依赖：

```csharp
context.EffectContext.IsExtraRoomSettlementActive
```

其中 `TriggerSelectedRoomSettleEffect` 还通过字符串判断是否包含：

```csharp
card.Data.settleEffect.Contains("TriggerSelectedRoomSettle")
```

**风险**

字符串判断对命名、复合效果、未来重命名都比较脆。额外结算如果继续扩展，递归保护会越来越难维护。

**建议**

做一个统一的额外结算执行器，集中管理：

- 当前结算深度。
- 当前来源效果。
- 是否允许嵌套。
- 哪些效果在额外结算中应跳过。

至少先把字符串判断封装为 `CardEffectFactory.ContainsEffect(effectString, effectId)`，避免直接 `Contains`。

---

### 5. 运行时 UI 保底生成与 Inspector 必填策略混用

**相关文件**

- `Assets/Scripts/Runtime/UI/Settlement/UISettlementSequenceController.cs`
- `Assets/Scripts/Runtime/UI/UIManager.cs`
- `Assets/Scripts/Runtime/UI/UIBoardPanel.cs`
- `Assets/Scripts/Runtime/UI/UIHandPanel.cs`

**现象**

有些 UI 缺引用时会运行时创建，例如 settlement transfer label。有些 UI 缺引用时直接抛异常，例如奖励面板和商店面板。

**判断**

这个方向本身合理：主流程必需组件应快速失败，视觉增强组件可以降级。但目前规则主要写在代码里，没有统一约定。

**建议**

在文档中明确 UI 引用等级：

1. **必填主流程**：缺失直接阻断，如奖励、商店、拖拽控制器。
2. **可降级表现**：缺失时跳过或运行时创建，如动效 label、popup layer。
3. **调试/体验增强**：缺失仅 warning，如 Feel feedback、额外音效。

## 四、结构优化建议

### 1. 拆分 `TurnManager`

**相关文件**

- `Assets/Scripts/Runtime/GameFlow/TurnManager.cs`

`TurnManager` 当前已经超过 1600 行，承载职责包括：

- 准备阶段
- 行动阶段
- 出牌验证
- 出牌执行
- 结算处理
- 结算 UI 批次生成
- 贷款
- 奖励三选一
- 商店
- 临时手牌清理
- 动画等待
- 事件订阅

建议拆分顺序：

1. `CardPlayResolver`：负责 `ValidatePlay`、`PlayCard`、扣费、即时效果、入弃牌。
2. `SettlementProcessor`：负责房间/合同结算、销毁、贷款、生成 `UISettlementPlaybackBatch`。
3. `RewardFlowController`：负责奖励池、奖励选择等待、奖励入手动画。
4. `ShopFlowController`：负责商店开启、购买、关闭、临时牌清理。

如果短期不想大拆，可以先使用 partial 按主题拆文件，降低单文件认知负担。

---

### 2. 抽公共的金钱效果 helper

**相关文件**

- `Assets/Scripts/Runtime/Card/Effects/*.cs`
- `Assets/Scripts/Runtime/Card/ICardEffect.cs`

很多效果重复执行：

```csharp
context.MoneyManager.AddMoney(amount);
context.SettlementCapture.RecordDelta(amount, sourceName);
Debug.Log(...)
```

建议集中为：

```csharp
EffectMoney.Add(context, amount, source, reason);
EffectMoney.Reduce(context, amount, source, reason);
```

收益：

- 统一 `source == null` 行为。
- 统一 SettlementCapture 行为。
- 统一日志标签。
- 减少新效果复制旧 bug 的概率。

---

### 3. `CardEffectRegistration.EnsureRegistered()` 应具备幂等早退

**相关文件**

- `Assets/Scripts/Runtime/Card/CardEffectRegistration.cs`

当前 `EnsureRegistered()` 每次调用都会重新注册所有效果。由于字典覆盖，短期没有明显 bug，但 `IsRegistered` 的语义是“已注册后不需要重复注册”。

建议加：

```csharp
if (IsRegistered)
{
    return;
}
```

测试场景仍可通过 `CardEffectFactory.ClearAll()` 和 `MarkUnregisteredForTesting()` 重置。

## 五、测试与控制台发现

### 当前控制台

当前 Unity Console 没有 error，存在 warning：

1. `[Image Feedback] The image feedback on SourceTriggeredPlayer doesn't have a BoundImage...`
2. `[MoneyManager] ReduceMoney received non-positive amount: 0`
3. Unity MCP 对 `TransformHandle` 序列化的 warning，属于工具侧警告。

建议优先处理第 2 项，因为它来自业务逻辑且会持续出现。

### 测试覆盖现状

已有测试集中在：

- CardLibrary
- Feedback
- Save
- Settlement
- Tooltip

相对缺少测试的区域：

- `TurnManager` 主流程。
- 随机事件执行卡牌效果。
- `SelectedRoom` 生命周期。
- 0 费用卡出牌。
- 拖拽提交期间状态变化。
- 商店购买、关闭、临时牌清理。
- 奖励选择等待与结算完成事件。

建议优先补最小测试：

1. 随机事件执行 `AddMoney;100` 不抛异常。
2. 房间目标效果执行后，`SelectedRoom` 能恢复。
3. 0 费用卡出牌不产生 warning，且可以正常进入弃牌或上场。
4. 奖励选择完成后只发布一次 `TurnEnded`。

## 六、建议处理顺序

### 第一批：立即修复

1. 修复所有效果类中直接访问 `source.Data` 的空引用风险。
2. 给 `SelectedRoom` 加作用域恢复。
3. 处理 `ReduceMoney(0)` warning。
4. 给 `CardEffectRegistration.EnsureRegistered()` 加幂等早退。

### 第二批：收敛重复防护

1. `UIManager` 抽 `ResetTransientInteraction()`。
2. 奖励/商店面板校验集中化。
3. 额外结算递归保护封装，不再散落字符串判断。
4. 效果参数解析统一 helper。

### 第三批：结构拆分

1. 拆 `TurnManager` 的商店模块。
2. 拆 `TurnManager` 的奖励模块。
3. 拆 `TurnManager` 的结算模块。
4. 将卡牌出牌解析从 `TurnManager` 中剥离。

## 七、风险分级摘要

| 优先级 | 问题 | 影响 |
| --- | --- | --- |
| 高 | 随机事件执行普通效果时 `source == null` | 可能直接 NRE |
| 高 | `SelectedRoom` 未恢复 | 可能误作用旧房间 |
| 中 | 0 费用卡 warning | 控制台污染，掩盖真实问题 |
| 中 | 效果参数解析分散 | 导表/启动错误信息不稳定 |
| 中 | `TurnManager` 过大 | 后续功能易互相影响 |
| 低 | UI 重置逻辑重复 | 维护成本增加 |
| 低 | 文档旧路径 | 新人/自动化任务易迷路 |
