# 全量代码 Review（基于交付优先工程原则）

> 审查日期：2026-03-30
> 审查范围：Assets/\_Assets/ 下全部业务代码（约 141 个 .cs 文件）
> 审查依据：delivery-first-code-guardrails skill（8 条原则）

---

## 总体评价

项目结构清晰，模块边界合理，核心链路（回合流程 → 出牌 → 结算 → 还贷）逻辑完整。Martian 框架（Feedback/Tooltip/Localization）作为独立插件模块设计得当，职责分明。以下按原则逐条审查。

---

## 原则 1：交付优先 — 主链路稳定性

### P0：`CardEffectRegistration.EnsureRegistered()` 会重复注册

`GameManager.Awake()` 每次调用 `EnsureRegistered()`，但该方法直接覆盖已有注册（`_registry[effectId] = factory`），没有幂等保护。当前不会报错，但语义上不是 "Ensure"。

**建议**：加一个 `_registered` flag，真正做到幂等：

```csharp
private static bool _registered;
public static void EnsureRegistered()
{
    if (_registered) return;
    _registered = true;
    // ... Register calls
}
```

### P0：`Singleton<T>` 静态字段在 Domain Reload 关闭时残留

`_applicationIsQuitting` 是 `static bool`，如果项目关闭了 Domain Reload（Unity 2021+ 常见优化），这个标志不会重置，导致下次 Play 时 `Instance` getter 直接返回 null。

**建议**：补 `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` 重置：

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
private static void ResetStatics()
{
    _instance = null;
    _applicationIsQuitting = false;
}
```

### P1：`ObjectPooler` 没有继承 `Singleton<T>`

`ObjectPooler` 自己手写了单例逻辑（`Instance = this`），与项目其他 Manager 的 `Singleton<T>` 模式不一致。且没有 `_applicationIsQuitting` 保护和 `OnDestroy` 清理。

**建议**：统一继承 `Singleton<ObjectPooler>`，或至少补 `OnDestroy` 中 `Instance = null`。

## 原则 2：复用优先，抽象谨慎

### P1：`ObjectPooler.ReturnToPool` 中 `queue.Contains(objectToReturn)` 是 O(n) 操作

`Queue<GameObject>.Contains()` 是线性扫描，如果池很大会有性能问题。这个检查的意图是防止重复入队。

**建议**：用 `_spawnedObjectsTag` 的移除结果来判断是否已回收过（当前逻辑已经在 Remove 后 Enqueue，重复调用时 `TryGetValue` 会失败），这个 `Contains` 检查可以安全移除。

### OK：Martian 框架三模块（Feedback/Tooltip/Localization）

拆分合理，通过 Service Locator + Null Object 模式解耦，asmdef 边界清晰。Integration 层做适配翻译。**这部分设计良好，无需改动。**

## 原则 3：关键问题尽早暴露

### P0：`GameManager.InitializeSystems()` 中 BoardManager/DeckManager null 时静默跳过

```csharp
if (Board.BoardManager.Instance != null)  // 静默跳过
{
    Board.BoardManager.Instance.Initialize(...);
}
```

BoardManager 和 DeckManager 是核心系统，如果场景中缺失，后续所有逻辑都会崩溃。这里用 `if != null` 静默跳过属于 **掩盖关键配置缺失**。

**建议**：改为 fail-fast：

```csharp
if (Board.BoardManager.Instance == null)
{
    Debug.LogError("[GameManager] BoardManager 未在场景中配置，游戏无法启动");
    return;
}
```

### P1：`TurnManager.ExecuteSettlePhase()` 中 `GetAllFieldCards()` 每次创建新 List

`BoardManager.GetAllFieldCards()` 和 `room.GetAllCards()` 每次都 `new List<>` + `AddRange`。在结算阶段多次调用（296 行又调了一次），产生不必要的 GC 压力。

**建议**：考虑传入一个复用的 `List<CardInstance>` 或在 BoardManager 中缓存。

### P1：`AwardOneCardFromThreeOptions` 中 `.ToList()` 和 LINQ 在结算热路径

```csharp
var source = boosted
    ? allCards.Where(c => c.rarity >= CardRarity.Rare).ToList()
    : allCards.ToList();
```

每回合结算都会 `.ToList()` 创建临时集合。`allCards.Values` 本身已经是 `IReadOnlyDictionary.Values`。

**建议**：用临时 `List` 复用，或直接从 `_cards` 随机抽取避免整体拷贝。

## 原则 4：边界清晰，职责单一

### P1：`TurnManager.ExecuteSettlePhase()` 职责过重（~180 行）

这个方法同时负责：

1. 房间结算 + capture
2. 合同结算
3. 卡牌耐久递减 + 销毁
4. 场上等待回合递减
5. 手牌等待回合处理
6. 还贷计算
7. 奖励卡发放
8. 结算动画编排

这是整个项目中最长、职责最密集的方法。任何一个子步骤出问题，调试成本很高。

**建议**：不需要大重构，但建议把 `ProcessRoomSettlement`、`ProcessContractSettlement`、`ProcessDurabilityAndCleanup`、`ProcessLoanPayment`、`ProcessReward` 提取为私有方法，保持 `ExecuteSettlePhase` 作为编排入口。

### P2：`UICardView.cs`（~720 行）承担了过多 UI 构建逻辑

这个文件同时负责：卡牌渲染、badge 系统、皮肤查找、tooltip 绑定、drag handler 绑定、上下文切换。作为项目中最复杂的 UI 组件，如果后续需要新增卡牌展示变体，这里会成为瓶颈。

**当前可接受**，但标记为未来风险点。

## 原则 5：Unity 与实时系统工程卫生

### P0：`DeckManager.Draw()` 中 `_drawPile.RemoveAt(0)` 是 O(n)

```csharp
var card = _drawPile[0];
_drawPile.RemoveAt(0);  // List 头部删除，后续所有元素前移
```

每次抽牌都是 O(n) 操作。如果牌库有 50+ 张牌，每回合抽 3-5 张，这是可观测的性能浪费。

**建议**：从尾部抽取（pop last），或用反转索引：

```csharp
var card = _drawPile[^1];
_drawPile.RemoveAt(_drawPile.Count - 1);
```

Shuffle 已经随机化了顺序，从尾部取和从头部取效果相同。

### P1：`SpawnRandomTenantInSelectedRoomEffect` 每次执行都重建租客池

```csharp
var allCards = CardDatabase.GetAll().Values;
var tenantPool = new List<CardData>();
foreach (var c in allCards) { if (c.cardType == CardType.Tenant) tenantPool.Add(c); }
```

如果这个效果在结算期间被多张卡触发，每次都会遍历整个数据库。

**建议**：在 CardDatabase 中缓存按类型分组的视图，或在效果类中做懒缓存。

### P1：`UISequenceTextController` 运行时创建 Canvas

每个浮动文字序列都可能创建新的 Canvas + CanvasScaler 对象。如果频繁触发，会产生大量 Canvas rebuild。

**当前可能足够**（取决于触发频率），标记为监控点。

## 原则 6：代码质量与可维护性

### P1：`EffectExecutionContext.SelectedRoom` 是共享可变状态

`GameContext.EffectContext.SelectedRoom` 在 `PlayCard` 时被设置，所有效果执行期间共享。如果某个效果内部改变了 `SelectedRoom`，后续效果会受影响。

**当前未观察到实际问题**，但这是一个隐含的执行顺序依赖。建议在关键位置加注释说明这个约束。

### P2：`CardData` 中 `cardName` / `description` 的 `[FormerlySerializedAs]` + 双属性

```csharp
[FormerlySerializedAs("cardName")]
public string defaultName;
// ...
public string cardName => defaultName;
public string description => defaultDescription;
```

`FormerlySerializedAs` 是迁移期工具，`cardName` / `description` 属性保留了旧接口。如果迁移已完成，这些可以清理。

**建议**：确认所有 `.asset` 文件都已重新序列化后，移除 `FormerlySerializedAs` 和旧属性别名。

### P2：部分效果类的日志语言不统一

`AddMoneyEffect` 用 `"[效果] 增加金钱"`，`ExpandSlotEffect` 用英文 `"[RoomSlot] Room {RoomIndex}"`。不影响功能，但增加了日志过滤的复杂度。

**建议**：统一用中文或英文前缀，推荐 `[Effect]` 前缀统一格式。

## 原则 7：关键位置注释

### P1：`TurnManager.ExecuteSettlePhase()` 缺少结算流程注释

这是整个游戏最核心的方法，但几乎没有注释解释结算的业务顺序（为什么先算房间再算合同？为什么耐久在结算效果之后递减？）。

**建议**：在方法开头补一段结算流程概述注释：

```csharp
// 结算阶段执行顺序：
// 1. 逐房间结算：基础租金 → settleEffect → 耐久递减
// 2. 合同结算：settleEffect → 耐久递减
// 3. 清理销毁卡牌（耐久归零 / 等待到期）
// 4. 手牌等待回合处理
// 5. 还贷检查（每 N 回合）
// 6. 奖励卡发放
// 7. 结算动画编排（如有 UI 播放则等待完成）
```

### P1：`SettlementCaptureContext` 的 Begin/Complete 协议缺少说明

这是一个有状态协议（必须 Begin → Record* → Complete），但接口上没有注释说明调用约束。

## 原则 8：验证

### 已有的验证（做得好）

- `GameManager.ValidateLoadedCardEffects()` — 启动时校验所有卡牌效果配置，fail-fast
- `CardTargeting.TryValidateConfiguredTargetKind()` — 校验 targetKind 配置一致性
- `CardDatabase.LoadAll()` — 重复 ID 检查，null 检查
- `TurnManager.ValidatePlay()` — 出牌前完整校验链

### 缺失的验证

- **GameConfig 值域校验**：`loanInterval = 0` 会导致 `_currentTurn % 0` 除零异常（虽然当前配置里是 5，但没有保护）
- **CardData.durability/waitTurns 负数**：没有校验，负数耐久的卡牌永远不会被销毁（`card.CurrentDurability--` 会一直递减到负无穷）

## 做得好的部分

1. **卡牌效果工厂 + 注册表模式** — 干净的字符串 → 效果映射，支持组合效果（`|` 分隔）和启动时全量校验
2. **结算 Capture 机制** — `SettlementCaptureContext` 实现了"逻辑即时生效 + UI 延迟播放"的解耦
3. **Martian 三模块的插件化设计** — Service Locator + Null Object + asmdef 隔离，可独立测试和替换
4. **`CardPlayValidationResult` 值类型** — readonly struct 做校验结果，零 GC 且语义清晰
5. **EventBus 的 Domain Reload 保护** — `[RuntimeInitializeOnLoadMethod]` 清理残留订阅
6. **启动时全量校验卡牌配置** — 把配置问题提前到启动期暴露
