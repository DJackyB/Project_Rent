# 项目风险与Review评估（2026-03-24）

## 评估范围

- 基于当前仓库代码、场景、资源和现有文档。
- 结合外部 review 截图，但以仓库实际实现为准。
- 判断前提是“3 个月短周期、先稳核心循环、中文优先、不过度通用化”。

## 当前状态说明

- 已处理：
  - `loanGrowthFactor` 已显式落到 [GameConfig.asset](../../Assets/_Assets/Data/Config/GameConfig.asset)。
  - 效果字符串已经补上启动期和导表期校验。
  - `GameOver` 时已经由 [GameManager.cs](../../Assets/_Assets/Scripts/Core/GameManager.cs) 主动停掉运行中的 `FSMOwner`。
  - 房间 UI 槽位已经改为跟随 `RoomSlot` 实际容量生成，不再写死 `1 租客 + 3 设备`。
  - 出牌目标类型已经从运行时字符串推断切到 `CardData.targetKind + CardTargeting`。
  - 导表不再自动猜 `targetKind`，未知 `cardType` / 缺列 / 非法值都会直接中断。
  - 启动期卡牌校验失败会直接中断初始化。
- 仍未处理完：
  - 中文玩家可见文案和字体链路。
  - 合同系统内容闭环。
  - 正式版前的 Debug 隔离。

## 总体结论

- 项目已经有可运行的核心循环，当前最重要的不是“做得更通用”，而是让现有链路更可依赖。
- 优先级最高的工作仍然是：
  - 数据一致性
  - 导表与启动期校验
  - 核心流程停机与错误边界
  - 玩家可见中文链路
- 暂时不建议把大量时间投入到大规模架构重构、完整对象池化或提前为 deckbuilding 做大改。

## P1：应尽快处理的风险

### 1. 目标类型已显式化，但团队流程还要彻底跟上

证据：

- [CardData.cs](../../Assets/_Assets/Scripts/Card/CardData.cs) 已新增 `targetKind`。
- [CardTargeting.cs](../../Assets/_Assets/Scripts/GameFlow/CardTargeting.cs) 已成为运行时统一入口。
- [CardDataImporter.cs](../../Assets/_Assets/Scripts/Editor/CardDataImporter.cs) 现在已要求 `targetKind` 必填，并在非法时直接失败。

风险：

- 代码层已经不再自动兜底。
- 剩余问题主要是团队录表习惯和存量表格是否完全切到新规则。

结论：

- 采纳外部 review，且已经进入严格执行阶段。
- 下一步重点是把旧表和旧流程完全迁干净。

### 2. 导表与配置校验仍需继续补语义层检查

证据：

- [CardDataImporter.cs](../../Assets/_Assets/Scripts/Editor/CardDataImporter.cs) 已能校验效果字符串。
- 未知 `cardType` 现在会直接中断导表。

风险：

- 静默回退已经基本拿掉。
- 当前校验仍偏“格式正确 + 关键语义一致”，还不是完整玩法验证。

结论：

- 强烈采纳外部 review。
- 下一批建议优先看更贴近玩法结果的语义验证，而不是继续保留回退。

### 3. `GameOver` 运行时已可停机，但图本身还没闭环

证据：

- [Condition_CheckGameOver.cs](../../Assets/_Assets/Scripts/GameFlow/NodeActions/Condition_CheckGameOver.cs) 已存在。
- [SampleScene.unity](../../Assets/Scenes/SampleScene.unity) 当前 FSM 图仍未显式接出 `GameOver` 分支。
- [GameManager.cs](../../Assets/_Assets/Scripts/Core/GameManager.cs) 现在会在 `GameOver` 事件时停掉 FSM。

风险：

- 实际运行已不再继续空转。
- 但状态机资产本身的表达仍不完整，后续维护时容易误判现状。

结论：

- 这条仍是高优先级，但已经从“功能缺口”降为“表达不完整”。

### 4. 中文优先目标与当前玩家可见文案不一致

证据：

- 当前 UI 固定文案仍有较多英文。
- 文档目标已经明确近期以中文优先。

风险：

- 如果近期面向中文玩家试玩，这会直接影响体验，不是可以长期拖延的债。

结论：

- 采纳外部 review。
- 建议尽快补中文字体与关键界面文案。

## P2：应记录并按节奏处理的结构债

### 1. 房间容量与 UI 槽位不一致的主问题已处理

证据：

- [RoomSlot.cs](../../Assets/_Assets/Scripts/Board/RoomSlot.cs) 持有真实容量。
- [UIRoomView.cs](../../Assets/_Assets/Scripts/UI/UIRoomView.cs) 已按真实容量动态生成槽位。

剩余风险：

- 这次解决的是“显示槽位数量”问题，不等于 UI 已经完全 prefab 化或房型系统已经完成。

结论：

- 外部 review 这条已被采纳并落地主要修复。

### 2. 合同系统代码预留较多，但内容尚未闭环

证据：

- [BoardManager.cs](../../Assets/_Assets/Scripts/Board/BoardManager.cs) 有合同列表。
- [TurnManager.cs](../../Assets/_Assets/Scripts/GameFlow/TurnManager.cs) 有合同出牌和结算分支。
- `Assets/Resources/Cards` 里当前没有 `Contract` 类型资产。

风险：

- 很容易让人误判“合同系统已经完成”。

结论：

- 采纳外部 review。
- 建议在文档与任务列表中把它明确标记为“代码预留，内容未接”。

### 3. `SelectedRoom` 仍是全局临时状态

证据：

- [TurnManager.cs](../../Assets/_Assets/Scripts/GameFlow/TurnManager.cs) 出牌时仍写入 `context.EffectContext.SelectedRoom = targetRoom`。

风险：

- 如果未来出现“选一次房间，后续多个阶段持续引用”的设计，这里会成为风险点。

结论：

- 这是中期结构债，不建议现在为此大改，但应在新增这类玩法前先处理。

### 4. 运行时补节点仍然较多

证据：

- [UIManager.cs](../../Assets/_Assets/Scripts/UI/UIManager.cs)、[UIBoardPanel.cs](../../Assets/_Assets/Scripts/UI/UIBoardPanel.cs)、[UIRoomView.cs](../../Assets/_Assets/Scripts/UI/UIRoomView.cs) 等仍包含运行时兜底创建逻辑。

风险：

- 原型期效率高。
- 中后期会抬高排错和美术协作成本。

结论：

- 条件采纳外部 review。
- 建议逐步把高频关键引用显式化，不做一刀切重构。

## 建议处理顺序

1. 补中文字体与玩家可见关键文案。
2. 明确合同系统是“预留”还是进入开发排期。
3. 正式版前隔离 Debug 快捷键与调试入口。
4. 继续清理仍依赖运行时补节点的关键 UI 引用。

## 结论性建议

- 这个项目现在最值得投入的方向是“让现有系统更可靠”，而不是“让系统看起来更高级”。
- 后续优化应继续围绕三件事展开：
  - 正确性
  - 校验
  - 文档与最小必要抽象
