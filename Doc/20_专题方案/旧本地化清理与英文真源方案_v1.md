# 旧本地化清理与英文真源方案 v1

> 状态：方案稿，未落地  
> 目标：移除当前旧的运行时本地化链路，把项目先收口到“英文单真源”，未来接多语言时再重新接模块化方案

## 目标

- 删除当前旧的本地化运行时链路。
- 把玩家可见文本先统一收口到英文真源。
- 去掉“中文 / 英文切换”和“按语言切字体”的现有逻辑。
- 为未来重新接入多语言保留清晰边界，但这次不做多语言本身。

## 非目标

- 这次不接 `Martian.Localization`。
- 这次不接 `com.unity.localization`。
- 这次不做语言切换 UI。
- 这次不做键值表、翻译表、外部文案资源导入。

## 推荐收口方式

不建议把英文文案直接散落回各个脚本。

更稳的做法是：

1. 删除“本地化系统”的概念
2. 保留“统一英文文本入口”的概念

也就是说：

- 删掉 `LocalizationManager`
- 删掉 `UIFontCatalog`
- 删掉当前带语言分支语义的 `UIStrings`
- 新建一个不带本地化含义的 `GameText` 或 `UITextCatalog`

这个新入口只负责：

- 提供当前项目的英文玩家可见文案
- 不负责切语言
- 不负责字体切换
- 不负责任何多语言状态

这样做的好处是：

- 先把旧本地化逻辑清干净
- 不会把英文字符串重新散落到几十个脚本里
- 未来如果重新接多语言，只需要把 `GameText` 这一层替换成 key-based provider，而不是再全项目搜字面量

## 建议分阶段实施

### 阶段 1：确定新的英文真源

新增一个英文文本入口，例如：

- `Assets/_Assets/Scripts/UI/GameText.cs`

职责：

- 提供当前 UI、流程、奖励、结算、提示、GameOver 等固定英文文案
- 不暴露任何 `UseChinese`、`LanguageChanged`、`CurrentLanguage` 之类状态

这一层的内容大致替代现在的：

- [LocalizationManager.cs](../../Assets/_Assets/Scripts/UI/LocalizationManager.cs)
- [UIStrings.cs](../../Assets/_Assets/Scripts/UI/UIStrings.cs)

### 阶段 2：移除旧运行时本地化链路

删除或停用以下内容：

- `LocalizationManager`
- `UIFontCatalog`
- `UIManager` 里的 `LanguageChanged` 订阅
- 各 UI 脚本里的 `RefreshLocalization()` 入口
- 所有基于“当前语言状态”分支设置文案或字体的逻辑

受影响重点文件通常包括：

- [UIManager.cs](../../Assets/_Assets/Scripts/UI/UIManager.cs)
- [UICardRewardPanel.cs](../../Assets/_Assets/Scripts/UI/UICardRewardPanel.cs)
- [UIGameOverPanel.cs](../../Assets/_Assets/Scripts/UI/UIGameOverPanel.cs)
- [UITopBar.cs](../../Assets/_Assets/Scripts/UI/UITopBar.cs)
- [UIPhasePanel.cs](../../Assets/_Assets/Scripts/UI/UIPhasePanel.cs)
- [UICardView.cs](../../Assets/_Assets/Scripts/UI/UICardView.cs)
- 所有调用 `UIStrings.*` 的脚本

### 阶段 3：把玩家可见中文统一改成英文

处理范围包括两类：

1. 通过 `UIStrings` 输出的现有玩家文案
2. 直接写死在代码里的中文字符串

建议优先处理玩家可见文案，再决定是否顺手把开发日志/错误信息也统一成英文。

如果按“仓库整体语言统一”为目标，可以一并把这些也改掉：

- `Debug.LogError(...)`
- `Debug.LogWarning(...)`
- Inspector 提示字段的中文说明

但如果只想先处理玩家体验，开发日志和 Inspector Header 可以留到下一轮。

### 阶段 4：清理场景和验收入口

当旧本地化逻辑删除后，要同步收口：

- 语言切换按钮或相关入口
- 文档中的“当前本地化真源”描述
- UI 手工验收里与切语言相关的步骤

需要更新的文档至少包括：

- `Doc/10_模块梳理/06_UI系统.md`
- `Doc/10_模块梳理/11_本地化模块.md`
- `Doc/10_模块梳理/UI手动配置与验收.md`
- `Doc/30_评估审查/主干合并后完整Review_2026-03-30.md`

## 对未来多语言接入的建议

等未来真的要重新接多语言时，再做下面这一步：

1. 保留 `GameText` 这层调用面
2. 把其内部从“直接返回英文字符串”替换成“按 key 向新本地化系统取值”
3. 再决定是否启用 `Martian.Localization` 或 Unity Localization

这样未来接入时：

- 不需要再回头把全项目 raw string 再收口一次
- 不需要把旧的中英混合分支重新 resurrect
- 可以从一个干净的英文单真源状态切到真正的 key-based 多语言

## 风险与注意点

- 如果直接删除 `UIFontCatalog`，要确认当前 TMP 默认字体对英文 UI 足够可用。
- 如果代码里有“中文不仅是显示文案、还参与逻辑判断”的地方，要先清掉这种隐式耦合。
- 如果一步把所有日志、玩家文案、Inspector 注释都改英文，改动面会很大，建议拆两批：
  - 第一批：玩家可见文案与 UI 主链路
  - 第二批：日志、编辑器提示、注释与文档

## 推荐执行顺序

1. 建立 `GameText` 英文真源
2. 全量替换 `UIStrings` 调用
3. 删除 `LocalizationManager`
4. 删除 `UIFontCatalog`
5. 删除所有 `LanguageChanged / RefreshLocalization` 链路
6. 全局清理代码里的中文玩家文案
7. 更新文档和验收清单

## 我建议的最终形态

短期项目最稳的形态应该是：

- 运行时只有一套英文文本真源
- 没有语言状态
- 没有语言切换
- 没有“临时双语”分支
- `Martian.Localization` 保持已导入未接线，等未来真要上多语言时再正式接入

这会比“继续维护旧轻量本地化直到未来某天再换掉”更干净，也更符合你现在想要的边界。
