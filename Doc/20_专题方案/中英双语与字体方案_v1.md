# 中英双语与字体方案 v1

## 目标

- 当前阶段只支持中文、英文两种语言。
- 优先解决系统层和 UI 层的中英切换，不上过重的本地化框架。
- 在不自动修改现有 `.asset` 配置的前提下，让项目具备稳定显示中文的能力。

## 为什么当前不直接上 Unity Localization

- 这是 3 个月短周期项目，当前文案量和复杂度还不值得引入完整本地化工作流。
- `Unity Localization` 会带来表、引用、组件、编辑器工作流、资源管理等额外成本。
- 当前更适合用“轻量语言管理 + 统一 UI 文案入口 + 字体工具”的方案，先把高频问题收口。

## 当前落地方案

### 语言层

- 入口脚本：`Assets/_Assets/Scripts/UI/LocalizationManager.cs`
- 枚举：`Assets/_Assets/Scripts/UI/AppLanguage.cs`
- 语言来源：
  - 优先读取 `PlayerPrefs` 里的玩家选择。
  - 没有存档时，根据系统语言决定默认值。
- 当前语言切换通过 `LocalizationManager.SetLanguage(...)` 触发。
- 切换后通过 `LanguageChanged` 事件刷新 UI。

### 文案层

- 入口脚本：`Assets/_Assets/Scripts/UI/UIStrings.cs`
- 当前仅收口系统级、框架级、公共 UI 文案，例如：
  - 顶栏
  - 阶段名
  - 出牌区 / 合同区
  - 房间摘要
  - 结算跳字
  - Game Over
  - 空槽位提示
  - 卡牌通用字段标签
- 这类文案不再建议散落硬编码。

### 字体层

- 字体选择：`Source Han Sans SC / 思源黑体简体中文`
- 来源：Adobe 官方发布
- 许可：`SIL Open Font License 1.1`，可商用，适合当前项目阶段
- 当前保留的原始字体文件：
  - `Assets/Resources/Fonts/SourceHanSansSC-Regular.otf`
- 当前字体应用入口：
  - `Assets/_Assets/Scripts/UI/UIFontCatalog.cs`
- 设计原则：
  - 运行时优先使用项目内的中文字体资源。
  - 不自动去改现有 prefab / scene / TMP 默认字体 `.asset`。
  - 如果后续你要手动把 TMP 默认字体改成正式字体资产，可以自行配置，不和当前方案冲突。

### 字库工具层

- 入口脚本：`Assets/_Assets/Scripts/Editor/ChineseFontTools.cs`
- 菜单路径：`Tools/BaoZuPo/Fonts/Scan And Update Chinese Font Atlas`
- 工具职责：
  - 扫描 `UIStrings` 中的系统文案
  - 扫描 `CardData` 里的名称和描述
  - 扫描 prefab / scene YAML 中已有的 TMP 文本
  - 更新或创建 `Assets/Resources/Fonts/BaoZuPoChineseDynamic.asset`
- 这一步是手动触发，不会在我修改代码时自动去改 `.asset`。

## 当前已经覆盖的范围

- 顶栏：回合、资金、累计支出
- 阶段面板：准备 / 行动 / 结算、结束行动、等待中
- 棋盘面板：出牌区、合同区
- 房间面板：房间摘要、空租客槽、空设备槽
- 卡牌通用字段：费用、基础租金、等待、租期、耐久、类型
- 结算表现：基础、加成、倍率、最终
- Game Over 面板
- 运行时创建的 TMP 文本会自动应用中文字体

## 当前没有做的部分

- 卡牌名、卡牌描述的完整双语内容管理还没有独立出表。
- 当前卡牌内容仍然直接读取 `CardData.cardName` / `description`。
- 这意味着：
  - 系统 UI 已具备中英切换能力。
  - 内容层文案暂时还是“资源里是什么，就显示什么”。

## 下一阶段建议

### 阶段 1

- 保持当前轻量方案。
- 系统层和公共 UI 文案全部走 `UIStrings`。
- 不再新增新的英文硬编码。

### 阶段 2

- 把内容层文案独立到一份中英表，建议按 `cardId` 管理：
  - `cardId -> zhName`
  - `cardId -> enName`
  - `cardId -> zhDesc`
  - `cardId -> enDesc`
- 这样可以继续避免直接批量改现有 `.asset`。

### 阶段 3

- 如果后期文案量明显增大，再评估是否升级到更完整的本地化工作流。
- 在此之前，不建议为了“理论上的完整性”提前引入重量级方案。

## 失败策略

- 缺少系统文案 key：应尽快在 `UIStrings` 中补齐，不建议静默 fallback。
- 缺少字体字符：通过字库工具扫描并补字。
- 缺少内容层双语条目：未来内容表接入后，建议明确打出缺失标记，不要默默回退。

## 手动配置建议

1. 保留 `SourceHanSansSC-Regular.otf` 作为原始字体来源。
2. 需要正式 TMP 字体资产时，手动运行 `Tools/BaoZuPo/Fonts/Scan And Update Chinese Font Atlas`。
3. 如果你要把 TMP 默认字体切成正式中文字体资产，建议手动配置，不由代码自动改 `.asset`。
4. 后续若要做语言切换按钮，直接调用 `LocalizationManager.SetLanguage(AppLanguage.Chinese / English)` 即可。

## 结论

- 当前最合适的是“轻量双语方案”，不是“完整本地化框架”。
- 这套方案已经能先解决系统 UI 中英切换和中文字体显示问题。
- 内容层双语先预留结构，等你确认文案来源后再接入独立表。
