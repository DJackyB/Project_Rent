- UI 面板长什么样、接到哪个场景。

## 运行时链路

当前主链路可概括为：

```text
CardEffect / 游戏逻辑
  -> RandomEventManager.TriggerEvent(...)
  -> EventBus.Publish(RandomEventTriggered)
  -> RandomEventPanel 展示标题、描述、选项
  -> 玩家点击选项
  -> EventBus.Publish(RandomEventOptionSelected)
  -> RandomEventEffectBridge 执行 option.effect
  -> 如有 nextEventId，再次触发下一事件
```

`Assets/Scenes/SampleScene.unity` 中已经存在：

这意味着随机事件不是“代码已入库未接线”，而是已经进入当前场景运行链路。

## 当前限制

- 当前随机事件标题、描述、选项文本直接来自导表资产，并没有像 `GameText` / `CardText` 一样统一走本地化表工作流。
- `RandomEventEffectBridge` 依赖最近一次触发事件缓存 `_currentEventData`，对未来更复杂的并发弹窗或多事件叠加并不友好。
- 当前没有单独的随机事件模块文档测试清单；出现回归时，更多依赖人工走场景验证。

## 手工验收点

1. 执行 `Tools/BaoZuPo/随机事件/导入随机事件数据` 后，确认 `Assets/Resources/RandomEvents/` 与 `Assets/Resources/RandomEventLibraries/` 资产被更新。
2. 进入 `SampleScene`，确认随机事件能弹窗展示标题、描述和选项。
3. 点击选项后，确认 `option.effect` 已执行，且 `nextEventId` 存在时能继续触发后续事件。
4. 新增或修改 Excel 行后，确认旧资产被覆盖而不是并存出脏数据。

## 修改准则

- 新增事件时，优先走 Excel -> 导表 -> Resources 资产链路，不要手工散改 `.asset`。
- 项目侧效果逻辑仍应复用 `CardEffectFactory`，避免在随机事件桥里再造一套效果解释器。
- 如果后续要做中英双语，随机事件文本应统一并入现有本地化工作流，而不是继续扩散新的“半独立文案源”。
