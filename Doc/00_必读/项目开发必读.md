# 项目开发必读

## 项目定位

- 这是一个 3 个月短周期项目，优先把核心循环做稳，不为远期可能性提前搭大框架。
- 允许为了当前玩法做定向实现，但要避免明显不合理、后续一改就碎的结构。
- 高重复、低成本、未来大概率继续使用的能力要及时抽成可复用组件。

## 开发准则

### 1. 先稳主链路，再谈优雅

- 优先保证 `准备 -> 行动 -> 结算 -> 奖励 -> 下一回合` 这条主链路稳定。
- 不要为了“未来可能会支持很多模式”提前做过度抽象。
- 允许临时占位，但必须在文档里明确标记占位范围。

### 2. 不重复造轮子

- 项目里已有能力能解决的问题，优先复用现有能力。
- Unity 自带方案、项目现有插件、成熟第三方插件能稳定完成的功能，优先评估接入，不重复手写。
- 涉及新的技术选型、插件接入、较大依赖时，先沟通再定。

### 3. 抽象要有边界

- 适合抽象：
  - 高频重复的 UI 组件和表现层能力。
  - 明确会继续扩展的数据校验与导表工具。
  - 低成本即可复用的通用流程节点。
- 不适合现在就抽象：
  - 为未来假设场景预埋的大型通用框架。
  - 当前只出现一次、短期也没有复用需求的逻辑。

### 4. 配置问题优先暴露

- 内容和配置错误优先直接报错并中断，不鼓励静默 fallback。
- 导表、启动期校验、运行时断言都应该尽量让问题尽早暴露。
- 如果一个兜底逻辑会掩盖真实问题，优先删兜底而不是继续吞错。

### 5. 非必要不要改动 `.asset`

- 非必要不要改动 `.asset` 文件，尤其是配置资产、场景、prefab、TMP 默认字体这类手工配置资源。
- 需要落地支持时，优先通过代码、文档、Editor 工具把链路补齐。
- 配置类资产默认由你手动调整，我这边尽量不自动改动。
- 如果确实必须动 `.asset`，应先说明原因，并把改动范围控制到最小。

### 6. 中文优先，但代码标识保持英文

- 近期玩家可见体验以中文优先，因此玩家可见文案和字体支持不能长期拖延。
- 代码里的类名、字段名、路径继续保持英文原名。
- 面向玩家的文案优先走统一文案入口，不要再散落硬编码。

## 当前仓库已有能力

- 流程驱动：NodeCanvas FSM 已用于回合流程驱动。
- 动效表现：DOTween 已用于拖拽反馈、跳字、HUD 动效。
- 导表工具：NPOI 已接入 Excel 读写与 `CardData` 生成。
- 事件系统：`EventBus` 已接入核心流程和 UI。
- UI 基础：UGUI + TMP 已形成现有界面基础。
- 资源复用：已有 `ObjectPooler`、运行时补节点链路和若干 UI 通用组件。

## 改动前检查清单

- 这次改动是在稳主链路，还是在提前做未来框架？
- 当前问题是否已经能被现有模块、现有插件、现有工具解决？
- 如果要抽象，这个抽象是否已经有足够重复点支撑？
- 这次改动是否会让数据、逻辑、UI 继续偏离？
- 这次改动是否会引入新的静默 fallback？
- 这次改动是否真的需要动 `.asset`？如果不是必须，就不要动。
- 玩家可见文案是否需要同步到中英双语入口？
- 是否需要同步更新模块文档或专题方案？

## 当前共识

- 回合主循环稳定性高于形式上的完美架构。
- 文档不是可选项，重要实现要落到 `Doc/`。
- 问题应尽量在导表、启动、调试期暴露，而不是拖到玩家运行时。
- 中文支持是当前体验债务的一部分，应持续补齐。
