# 工程文档与记录规范

## 概览

这个 skill 用来约束工程文档怎么写、写到哪里、什么时候更新、哪些内容不该混在一起。

核心目标：

- 文档成为维护入口，而不是历史噪音
- 当前实现、设计方案、风险评估、外部资料和开发日志各归各位
- 重要知识沉淀到可复用位置，不只留在聊天、提交记录或临时笔记里
- 手工配置和验收路径可查、可跟进、可交接

## 工作顺序

处理相关任务时，按下面的顺序思考：

1. 先判断这次信息属于长期规则、当前实现、专题方案、评估审查、外部参考还是历史记录。
2. 再判断它是否影响维护入口，而不是只影响临时沟通。
3. 如果会影响后续理解、接入、排错或验收，就必须沉淀到正式文档。
4. 如果只是时间性过程记录，放进归档，而不是挤占主目录。
5. 设计稿和方案文档必须标明落地状态，避免后续误读。

## 原则 1：文档不是附属物，是工程结构的一部分

- 重要实现、长期规则、模块边界、真源说明、验收方式都应落到正式文档。
- 不要把关键知识只留在聊天记录、提交说明或开发日志里。
- 后续维护者应能通过文档快速恢复上下文，而不是重新考古。

## 原则 2：当前实现优先写进“实现说明”

- 只要某个系统已经成为当前真实实现，就应更新到“模块说明”或“维护入口”文档。
- 不要让开发日志代替当前实现说明。
- 当前实现文档应帮助后来者快速回答：
  - 入口脚本在哪里
  - 真源在哪里
  - 依赖哪些系统
  - 当前限制是什么
  - 改动时要注意什么

### 常见错误

- 实际已经改完，但模块文档还是旧的
- 真实实现只记录在开发日志里
- 维护入口找不到当前接入点

## 原则 3：长期规则与项目共识集中维护

- 长期有效的开发原则、协作共识、改动前检查项，应集中维护在“必读”类文档。
- 不要把长期规则散落在专题方案、日志或临时评审文档里。
- 新规则如果未来仍然有效，应追加到长期规则文档，而不是继续复制到各处。

## 原则 4：专题方案必须标明落地状态

- 设计稿、演进方案、重构计划、专题讨论文档，必须明确标记：
  - 未落地
  - 部分落地
  - 已落地
  - 已废弃
- 如果文档同时包含“建议方案”和“当前实现”，必须清楚区分。
- 不标记状态的专题文档，后续极易被误读成当前真实实现。

## 原则 5：外部资料只做参考，不冒充真源

- Excel、PDF、原始表格、第三方文档、策划稿、截图等外部资料，只是参考资料。
- 它们不应自动被视为运行时真源或当前实现真相。
- 文档中要明确写清：
  - 哪些是参考资料
  - 哪些是运行时实际读取的内容
  - 哪些是导出物或派生结果

## 原则 6：时间性记录应归档，不污染维护入口

- 开发日志、阶段清单、临时决策记录、一次性排查过程等时间性强的内容，应统一归档。
- 主目录和维护入口文档应保留高信号、稳定内容。
- 归档的目标不是删除历史，而是避免历史噪音淹没当前真相。

## 原则 7：推荐的文档分区模板

下面是一套可迁移的工程文档结构模板：

### `00_必读`

放长期有效的内容：

- 项目原则
- 协作准则
- 改动前检查项
- 持续追加的长期规则

### `10_模块梳理`

放当前实现说明，作为维护入口：

- 关键入口脚本
- 核心数据结构
- 当前实现方式
- 与其他模块的依赖
- 当前限制与风险
- 修改准则
- 手工验收点

### `20_专题方案`

放专题设计与演进方案：

- 阶段性方案
- 抽离计划
- 演进建议
- 未来可扩展设计

要求：

- 必须写清当前是否已落地

### `30_评估审查`

放评估类文档：

- 风险分析
- review 结论
- 优化建议
- 外部审查意见

### `40_外部资料`

放参考资料：

- Excel
- PDF
- 需求附件
- 外部说明材料

要求：

- 明确标注它们不是当前实现真源

### `90_归档`

放时间性强的历史记录：

- 开发日志
- 阶段记录
- 已完成但不再作为维护入口的过程文档

## 原则 8：手工配置与验收必须文档化

- 对场景接线、Prefab 配置、Inspector 引用、资源挂载、启动顺序、模块启用步骤等无法完全由代码表达的内容，必须写成文档。
- 文档应至少包含：
  - 目标脚本或系统
  - 需要手工配置的字段或节点
  - 当前仍由运行时兜底的内容
  - 最短验收顺序
  - 模块缺席时的降级验收

## 原则 9：文档更新要跟随真实改动

出现以下情况时，应主动更新文档：

- 模块边界变化
- 真源变化
- 接入方式变化
- 手工配置步骤变化
- 降级行为变化
- 验收路径变化
- 长期规则新增或修正

如果这些内容变了但文档没变，后续维护成本会快速上升。

## 关键位置的中文注释建议

文档或代码中，以下位置建议补简洁中文说明：

- 当前实现与设计稿的区别
- 为什么某文档只是参考资料而不是真源
- 当前方案是否已经落地
- 这个手工步骤为什么不能省略
- 某个验收顺序为什么必须按此执行

## 输出要求

应用本 skill 时：

- 明确这次信息应该写到哪一类文档
- 优先更新“当前实现说明”，不要只写日志
- 专题文档必须写清落地状态
- 外部资料必须和真源分开描述
- 如果改动涉及手工接线或验收，必须把步骤写清楚

## 审查清单

提交前检查：

- 这次信息属于长期规则、当前实现、专题方案、评估审查、外部资料还是历史记录？
- 当前实现是否已经同步到维护入口文档？
- 是否错误地把开发日志当成当前实现说明？
- 专题文档是否明确写了落地状态？
- 外部资料是否被错误当成真源？
- 时间性内容是否已经归档，而不是堆在主目录？
- 手工配置和验收步骤是否已经文档化？

## 常见错误

- 关键知识只留在聊天或提交记录里
- 当前实现只写在日志，不写在模块说明
- 专题方案不写落地状态
- 外部参考资料被误当成真源
- 评估结论、设计方案、实现说明混在同一份文档里
- 手工接线流程没人写，导致代码改完仍不可用
