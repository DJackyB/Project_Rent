# 开新任务固定起手模板

下面这些模板用于在新功能、优化或修 bug 开始前，稳定触发 `$development-task-routing`。

使用方式：

- 直接复制一个模板
- 把尖括号里的占位内容替换掉
- 如果你已经知道某些约束或偏好，直接写进“背景”里

## 通用完整版

```text
用 $development-task-routing 处理这个任务。先自动判断是否需要进入 plan 模式；如果需要，先给我计划，再开始执行。把任务拆成适合主 AI、Claude Code、Codex 子 agent、Antigravity 或人工执行的子任务。大型决策必须先问我，不要默认拍板。接受显式配置、手工接线和人工步骤；非必要不要加 fallback、默认值吞错或保底防御。

任务类型：<新功能 / 优化 / bugfix>
任务目标：<你要达成什么>
非目标：<这次不做什么>
背景：<相关模块、现状、限制、已有思路>

启动时请先输出：
1. 是否进入 plan 模式，以及原因
2. 总目标和非目标
3. 真源、约束和主要风险
4. 需要我拍板的大型决策
5. 子任务拆分和执行者分派
6. 并行 / 串行关系
7. 需要人工执行或手工配置的部分
8. 联调和最终验收方式
```

## 新功能模板

```text
用 $development-task-routing 启动这个新功能。先判断是否需要 plan 模式；如果需要，先规划。把工作拆成方案、核心实现、辅助实现、配置接线、联调验收几个阶段，并分派给主 AI、Claude Code、Codex 子 agent、Antigravity 或人工。遇到架构、模块边界、长期配置或自动化方案这类大型决策时先问我。接受显式配置和手工步骤，非必要不要做保底防御。

新功能目标：<目标>
影响范围：<模块 / UI / 配置 / 数据>
非目标：<不做什么>
补充背景：<已有方案、真源、依赖、限制>
```

## 优化模板

```text
用 $development-task-routing 处理这次优化任务。先判断是否需要进入 plan 模式。请先识别优化目标、瓶颈范围和不能破坏的行为，再拆分任务并分派执行者。大型取舍必须先问我。接受显式配置和必要的手工步骤，非必要不要为了“更稳”而额外加 fallback。

优化目标：<性能 / 可维护性 / 结构 / 体验>
当前问题：<现象>
不能破坏的行为：<约束>
背景：<相关代码、模块、历史问题>
```

## Bug 修复模板

```text
用 $development-task-routing 处理这个 bug。先判断这是可以直接修的小 bug，还是需要进入 plan 模式的复杂 bug。如果是复杂 bug，请拆成复现、定位、修复、回归验证、人工验收几个阶段，并分派执行者。大型决策必须先问我。非必要不要加静默 fallback 或保底防御来掩盖真实问题。

问题现象：<现象>
期望行为：<应该怎样>
复现线索：<如何复现 / 哪些日志 / 哪些场景>
背景：<相关模块、最近改动、怀疑方向>
```

## 超短起手版

```text
用 $development-task-routing 处理这个任务：<一句话描述任务>。先自动判断是否需要 plan 模式；大型决策先问我；拆分并分派给主 AI、Claude Code、Codex 子 agent、Antigravity 或人工；接受显式配置和手工步骤，非必要不要加 fallback。
```
