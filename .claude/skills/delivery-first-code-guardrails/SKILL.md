# 交付优先的代码开发原则

## 概览

这个 skill 用来约束代码开发与重构时的工程判断。

目标不是追求“最花哨的设计”，而是帮助 AI 在真实项目中做出更稳、更清晰、更容易落地的决策：

- 优先保证主链路稳定可交付
- 复用现有结构，不默认推倒重来
- 只有在有证据时才做抽象
- 关键问题尽早暴露，不用静默兜底掩盖真实问题
- 保持职责边界清晰
- 优先保留维护者熟悉、项目现有的可读写法
- 明确验证方式
- 在关键位置补充简洁中文注释

## 工作方式

处理任务时，按下面的顺序思考和执行：

1. 先确认目标行为、约束条件和数据真源。
2. 先阅读现有代码路径，再决定是否需要结构调整。
3. 判断这次改动主要属于哪一层：
   - 核心逻辑
   - 展示或 UI
   - 数据或配置
   - 集成或胶水层
4. 选择能解决真实问题的最小改动方案。
5. 在靠近问题来源的地方补校验、保护或错误暴露。
6. 需要时同步更新测试、注释、文档或人工验收说明。
7. 输出时明确说明改了什么、为什么这样改、风险点是什么、验证了什么、还有什么需要人工跟进。

## 原则 1：交付优先

- 先保证主链路正确、稳定、可运行，再追求结构优雅。
- 优先解决真实问题，不为假想未来提前搭大框架。
- 如果简单方案已经足够，就不要为了“看起来高级”引入复杂抽象。
- 优先选择小而清晰、边界明确、容易验证的实现。

### 典型反例

- 为一个一次性需求先造通用框架
- 主流程还不稳定时就大量做架构升级
- 为未来也许会出现的扩展场景提前设计复杂层次

## 原则 2：复用优先，抽象谨慎

- 修改前先检查现有模块、工具、模式、基础设施是否已经能解决大部分问题。
- 优先扩展现有结构，而不是默认重建一套新系统。
- 只有在出现以下情况时才考虑抽象：
  - 已经有重复逻辑
  - 边界比较稳定
  - 确实存在明确扩展轴
- 抽象必须说明清楚：
  - 输入是什么
  - 输出是什么
  - 谁拥有它
  - 生命周期在哪里
  - 失败时如何表现

### 禁止事项

- 不要为了“通用性”把简单问题复杂化
- 不要引入没有明确收益的新依赖、新层次、新术语
- 不要只做“把代码搬到别处”的伪抽象

## 原则 3：关键问题尽早暴露

- 对缺配置、无效数据、错误接线、非法状态、契约不满足等问题，应尽早暴露。
- 不要用静默 fallback、默认值吞错、假装成功来掩盖真实问题。
- 校验尽量靠近问题来源。
- 只有被明确设计为“可选能力”的部分，才允许优雅降级。

### 可降级与不可降级

可降级的典型场景：

- 展示层效果缺失
- 可选 UI 能力缺失
- 非关键增强能力不可用

不可降级的典型场景：

- 核心业务逻辑
- 数据真源错误
- 关键配置缺失
- 生命周期或协议不成立

## 原则 4：边界清晰，职责单一

- UI 和表现层不承接核心业务规则。
- 核心逻辑不要紧耦合具体框架、渲染、存储、平台或第三方 SDK。
- 外部系统接入优先放在适配层、桥接层、服务边界后面。
- 数据真源必须明确，避免多个位置都像“唯一真实来源”。
- 事件流、数据转换、业务决策应尽量分开。

### 推荐分层

- 核心逻辑负责规则与状态
- 表现层负责展示与交互
- 集成层负责把外部能力翻译成内部可用接口
- 配置层负责显式声明，不隐藏契约

## 原则 5：Unity 与实时系统工程卫生

- 不要在热路径里做重复查找、重复分配和不必要的对象创建。
- 高频访问的组件、引用和结果应缓存。
- 可配置项优先显式声明，不依赖隐式推断或运行时碰运气补齐。
- 生命周期中的订阅与取消订阅、创建与清理必须成对出现。
- 对象销毁与托管资源释放都要处理到位。
- 不要把性能优化扩散到冷路径，避免为了微优化牺牲可读性。

### 重点关注区域

- `Update`、`FixedUpdate`、`LateUpdate`
- 高频 UI 刷新
- 频繁事件响应
- 大量对象生成与销毁
- 重复查找、字符串拼接、集合分配

## 原则 6：代码质量与可维护性

- 明确处理 nullability 和初始化责任。
- 使用最小访问修饰符，默认不要暴露实现细节。
- 编译器 warning 不应被当作噪音忽略。
- 优先不可变：
  - 不再重新赋值的字段用 `readonly`
  - 编译期常量用 `const`
- 可以在合适时使用现代语言特性：
  - `??`
  - `?.`
  - 模式匹配
  - 字符串插值
  - 集合初始化
  - 简单成员使用表达式体
- 语言特性只是工具，不是目标。
- 可读性、熟悉度、维护成本，优先级高于“语法更现代”。

### 风格改写原则

- 对于功能等价的风格改写，优先保留项目现有风格和当前维护者熟悉的写法。
- 不要为了“更现代”“更短”“更像高手代码”而重写已经稳定、清楚、易维护的代码。
- 如果 `for`、传统 `switch`、普通属性、显式 null 判断已经更直观，就可以继续保留。
- 只有在以下情况下才主动引入维护者可能不熟的新语法：
  - 明显减少真实 bug 风险
  - 明显提升可读性
  - 团队已经普遍熟悉
  - 代码库中已经大量使用并形成统一风格
- 如果新写法只是更短，但理解成本更高，应优先保留旧写法。
- 如果“现代写法”和“更容易理解”发生冲突，一律优先选择更容易理解的写法。
- 不要把 LINQ、表达式体、switch expression、模式匹配等写法视为默认更优；它们只有在确实更清楚时才值得使用。

### 注意事项

- 不要把某种语法写法当成机械教条
- 如果普通写法更直观，应优先可读性
- 现代写法的目标是减少样板代码，而不是制造阅读门槛
- 不要为了风格统一而重写稳定代码

## 原则 7：关键位置写简洁中文注释

- 默认优先靠命名和结构表达意图，不要堆砌无意义注释。
- 在关键位置必须补充简洁中文注释，帮助后续维护者快速理解意图。
- 注释应解释：
  - 为什么这样做
  - 这里的边界或约束是什么
  - 哪个隐含前提必须成立
  - 这里为什么不能轻易改
  - 当前是临时折中还是长期设计

### 适合写中文注释的位置

- 复杂状态切换
- 不明显的分支条件
- 协议、格式、序列化假设
- 生命周期耦合点
- 清理与回收约束
- 隐含不变量
- 临时兼容逻辑
- 已知风险点

### 不要这样写

- 不要把代码字面意思重复一遍
- 不要对简单赋值、简单判断逐行解释
- 不要写长篇废话式注释

## 原则 8：验证是变更的一部分

- 代码改动必须附带验证思路。
- 能自动化验证时优先自动化。
- 无法自动化时，要给出明确的人工验收步骤。
- 验证不能只看“能跑”，还要覆盖：
  - 主路径
  - 边界条件
  - 失败行为
  - 清理行为
  - 降级行为

## 审查清单

提交或收尾前检查：

- 主链路是否正确且稳定？
- 是否引入了掩盖真实问题的 fallback？
- 核心逻辑、UI、数据、集成边界是否仍然清晰？
- 数据真源是否仍然明确？
- 是否新增了没有明确收益的抽象或依赖？
- 生命周期、订阅、清理、资源所有权是否对称？
- 热路径里是否存在重复查找或额外分配？
- 验证是否覆盖到这次改动的真实风险？
- 是否只是做了功能等价但更难理解的风格改写？
- 关键逻辑处是否需要补一条简洁中文注释？

## 常见错误

- 为一次性问题搭通用框架
- 不理解现有结构就推倒重来
- 用默认值或静默降级掩盖配置问题
- 把业务规则塞进 UI 或胶水代码
- 没有稳定边界却强行抽象
- 在冷路径过度优化
- 为了“现代化”重写本来已经清楚的代码
- 代码改完却没有说明如何验证
- 写了很多无意义注释，却没有解释真正关键的约束

## 输出要求

应用本 skill 时：

- 优先给出直接、可维护、可验证的方案
- 简明说明权衡，不空谈
- 明确指出真实风险和未验证项
- 如果需要人工补配置或手工操作，要明确写出
- 在关键逻辑处补充简洁中文注释
