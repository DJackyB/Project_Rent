# 模块边界与配置原则

## 概览

这个 skill 用来约束模块设计、系统接入和配置落地时的工程判断。

核心目标：

- 模块边界清晰
- 接入方式显式
- 配置关系清楚
- 真源唯一明确
- 可选能力可降级，但核心能力不偷兜底

## 工作顺序

处理相关任务时，按下面的顺序思考：

1. 先判断这次改动属于核心能力、通用预设，还是项目集成层。
2. 先确认模块的输入、输出、安装点、注册点和生命周期。
3. 确认真源在哪里，哪些只是参考资料、缓存或派生结果。
4. 判断哪些引用必须显式配置，哪些可以暂时由运行时补齐。
5. 定义失败行为：直接报错、中断、还是只做受控降级。
6. 最后补验证方式：自动化检查、启动期校验、人工接线验收。

## 原则 1：模块按职责分层

推荐把可复用能力拆成三层：

1. 核心层
2. 预设层
3. 项目集成层

### 核心层

核心层只负责：

- 通用协议
- 基础数据结构
- 默认 runtime
- 真正跨项目通用的行为

核心层不应依赖：

- 具体业务语义
- 项目命名空间
- 项目事件定义
- 项目专属配置项
- 特定场景对象或 UI 结构

### 预设层

预设层用于承载已经被多次复用、语义稳定、跨项目仍然成立的高频能力。

适合放进预设层的内容：

- 通用 payload
- 通用 presenter
- 通用 sequence 或 formatting
- 稳定的默认实现组合

不适合放进预设层的内容：

- 当前项目独有的命名
- 只服务某一个玩法语义的逻辑
- 需要读取项目状态才能成立的规则

### 项目集成层

项目集成层负责：

- 项目语义翻译
- 事件到模块输入的转译
- content id、anchor、target key 解析
- 项目专属开关、映射和装配
- 项目自己的 presenter、adapter、bridge

判断标准：

- 如果脱离当前项目仍然成立，优先考虑核心层或预设层
- 如果它依赖项目语义，就必须留在项目集成层

## 原则 2：显式安装优于隐式生效

- 模块是否启用、何时启用、注册哪些能力，应由项目启动流程显式声明。
- 不要依赖“脚本存在就自动生效”的隐式机制。
- 安装步骤、注册顺序、依赖前提应能从启动链路中直接看出来。
- 启动失败时，应尽量在安装阶段暴露，而不是拖到第一次使用才报错。

### 推荐做法

- 显式调用安装器、bootstrap 或注册入口
- 把依赖前提写清楚
- 把模块接入点集中在少数明确位置

### 不推荐做法

- 分散式自动注册
- 不可追踪的隐式 side effect
- 模块缺失后仍假装系统已完成初始化

## 原则 3：显式配置优于运行时猜测

- 高频、易误配、排查成本高的引用，应优先显式配置。
- 稳定结构应尽量通过 Inspector、配置资源、注册表、映射表等方式声明。
- 不要依赖运行时扫描、猜测、动态补齐去维持长期结构。

### 优先显式配置的场景

- 核心引用
- 稳定 prefab 结构
- 关键 UI 节点
- 高复用配置
- 容易误配且出错成本高的对象

### 可以暂时运行时补齐的场景

- 原型阶段临时容器
- 纯展示 overlay
- 缺失后不影响主流程的低风险节点
- 仍在频繁改版、暂时不值得手工固化的结构

### 判断标准

如果一个节点反复误配、开始需要美术精修、或已经成为稳定结构，就应该从运行时补齐收敛到显式配置。

## 原则 4：真源必须唯一明确

- 外部资料、设计稿、Excel、配置资产、运行时缓存、派生数据、文档说明，这些角色必须明确区分。
- 参考资料不是运行时真源。
- 派生结果不是配置真源。
- 文档说明不是运行时真源。
- 真源路径必须唯一、清楚、可验证。

### 推荐做法

- 明确运行时实际读取的配置入口
- 明确编辑时的内容入口
- 明确导出、导表、生成物的责任边界
- 在文档中写清“参考来源”和“运行时真源”的区别

### 常见错误

- Excel、文档、资产、缓存同时像真源
- 运行时读的是生成物，但团队仍把参考表当唯一标准
- 某些字段依赖命名约定而不是显式配置

## 原则 5：可选模块允许受控降级

- 不是所有 fallback 都是坏事，但必须限制范围。
- 只有明确被设计为“可选能力”的模块，才允许 no-op 或展示层降级。
- 降级后允许失去表现，不允许改变核心业务结果。

### 合格的降级

- 某个展示模块缺席，只是少了显示效果
- 某个可选运行时服务不可用，但主逻辑仍然成立
- 缺少某个增强能力时，系统退回到稳定、可预期的最小行为

### 不合格的降级

- 配置缺失却自动猜测
- 契约不成立却继续往下跑
- 数据错误被默认值掩盖
- 核心逻辑因为 fallback 进入伪正常状态

## 原则 6：集成层负责翻译，不负责污染核心

- 外部系统、第三方 SDK、平台能力，应优先通过 adapter、bridge、service boundary 接入。
- 集成层的职责是翻译和装配，不是把外部概念扩散到核心层。
- 项目语义不应反向污染公共模块。

### 推荐职责分配

- adapter：把外部或项目语义转换成内部输入
- bridge：连接事件流和生命周期
- installer/bootstrap：负责显式安装与注册
- core service：负责稳定的内部能力

## 原则 7：配置与接线必须有验收路径

- 任何需要 Inspector 配置、Prefab 接线、注册顺序、手工启用步骤的系统，都必须有明确的验收路径。
- 如果自动化无法覆盖完整链路，应补最短人工验收顺序。
- 输出时要明确：
  - 哪些是代码改动
  - 哪些仍需手工配置
  - 缺失配置时会出现什么表现
  - 如何验证模块成功接入

## 关键位置的中文注释建议

以下位置建议补简洁中文注释：

- 为什么这个能力放在核心层而不是集成层
- 为什么这里需要显式安装
- 为什么这个引用必须显式配置
- 这里允许 no-op 降级的边界是什么
- 哪个字段才是真源，哪个只是派生或缓存

## 审查清单

提交前检查：

- 这个能力属于核心层、预设层还是项目集成层？
- 公共模块里是否混入了项目语义？
- 模块安装和注册是否显式、可追踪？
- 哪些引用是显式配置，哪些只是临时运行时补齐？
- 真源是否唯一明确？
- 是否错误地把参考资料当成运行时真源？
- 降级是否只影响展示，不影响核心流程？
- 是否写清了手工接线和验收方式？

## 常见错误

- 把项目业务枚举写进公共模块
- 模块自动生效但找不到接入入口
- 关键引用靠运行时猜测和扫描维持
- 把文档或参考表误当成运行时真源
- 把 fallback 用在核心契约缺失场景
- 没写清手工配置步骤，导致代码改完仍不可用
