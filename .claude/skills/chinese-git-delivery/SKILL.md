# Chinese Git Delivery

## Overview

在执行提交、推送或 PR 交付前，先收口范围，再用中文整理完整交付信息，避免出现“代码推上去了，但标题、详情、验证和风险没有说明白”的状态。

## Workflow

1. 先确认交付范围
- 查看当前分支、工作区状态、已修改文件和未跟踪文件。
- 区分“本次要交付的内容”和“用户未要求处理的残留内容”。
- 不要把无关改动、本机缓存、临时目录或其他线程产物一起带入。

2. 先决定交付载体
- 如果用户明确要求直接推当前分支，就按用户要求执行。
- 如果当前分支是 `main` 或跟踪主干，而用户没有明确要求直推主干，优先新建独立分支后再推送。
- 如果需要 PR，再在已推送分支基础上创建 PR。

3. 提交前整理中文信息
- 为 commit 准备中文标题和中文正文。
- 标题要短，聚焦本次改动的主结果，不写空话。
- 正文至少覆盖：
  - 改了什么
  - 为什么改
  - 验证情况
  - 未覆盖或剩余风险

4. 标准提交写法
- 中文标题建议使用：`feat:`、`fix:`、`refactor:`、`docs:`、`chore:` 这类前缀加中文摘要。
- 中文正文优先写事实，不写夸张描述。
- 如果测试没跑，要明确写“未运行”。
- 如果保留了用户未处理的文件或目录，要在最终对外说明里点明。

5. 推送时补齐交付信息
- 记录推送分支名、远端、提交 SHA。
- 如果创建 PR，PR 标题和详情也必须写中文。
- PR 详情至少覆盖：
  - 背景
  - 本次改动
  - 验证情况
  - 风险与注意事项
  - 后续建议（如果确实有）

6. 最终回报给用户
- 明确说明：
  - 提交标题
  - 提交 SHA
  - 推送到哪个分支
  - 是否创建 PR
  - 哪些内容没有包含进这次交付
- 如果因为环境限制没有跑测试或没有完成 push / PR，要直说。

## Guardrails

- 不要默认把无关未跟踪目录一起提交。
- 不要默认直推 `main`，除非用户明确要求。
- 不要省略验证状态；“没跑测试”也属于必须说明的信息。
- 不要只给标题，不给正文；也不要只给正文，不给交付结果。
- 如果改动里同时包含功能、文档、工具或 skill，标题和正文要把边界写清楚。

## Output Checklist

- commit 中文标题已写好
- commit 中文正文已写好
- staging 范围已核对
- 分支策略已说明
- push / PR 结果已记录
- 验证状态与剩余风险已说明
