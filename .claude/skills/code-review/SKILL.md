执行代码审查时：

1. **读取目标文件**的完整内容。

2. **读取项目规范**：优先查阅 `Doc/00_必读/` 目录下的文档了解项目编码规范。

3. **识别系统类别**（核心系统、卡牌系统、经济系统、UI系统、工具类），套用对应标准。

4. **评估编码规范**：
   - [ ] 公开方法和类有注释说明
   - [ ] 单个方法不超过 40 行（不含数据声明）
   - [ ] 圈复杂度在 10 以内
   - [ ] 依赖通过注入或 EventBus 解耦（避免直接持有其他 Manager 引用）
   - [ ] 配置值从 GameConfig 或 ScriptableObject 读取，不硬编码
   - [ ] 系统通过接口或事件暴露功能

5. **检查架构合规性**：
   - [ ] 依赖方向正确（Core ← GameFlow ← Board/Card/UI，不反向）
   - [ ] 模块间无循环依赖
   - [ ] UI 不持有游戏状态，通过 EventBus 监听
   - [ ] 跨系统通信使用 EventBus / GameEvents
   - [ ] 与项目已有模式一致（EventBus、Factory、FSM）

6. **检查 SOLID 合规性**：
   - [ ] 单一职责：每个类只有一个变化原因
   - [ ] 开闭原则：可扩展而不需修改（如 CardEffectFactory 模式）
   - [ ] 里氏替换：子类可替换父类
   - [ ] 接口隔离：无臃肿接口
   - [ ] 依赖反转：依赖抽象而非具体实现

7. **检查 Unity 常见问题**：
   - [ ] Update() 中无 GetComponent 调用（应在 Awake/Start 缓存）
   - [ ] 热路径无 GC 分配（字符串拼接、LINQ、new）
   - [ ] 正确处理 null（Unity 对象用 `== null` 而非 `is null`）
   - [ ] 协程有对应的停止逻辑，不泄漏
   - [ ] 使用 `[SerializeField] private` 而非 `public`

8. **输出审查结果**，格式如下：

```
## 代码审查：[文件/系统名称]

### 规范合规性：[X/6 通过]
[列出不合格项及行号]

### 架构：[CLEAN / 轻微问题 / 存在违规]
[列出具体架构问题]

### SOLID：[合规 / 存在问题]
[列出具体违规]

### Unity 专项问题
[列出 Unity 特有的问题]

### 优点
[做得好的地方——必须包含此节]

### 必须修复
[上线前必须解决的问题]

### 建议
[可选的改进项]

### 结论：[通过 / 建议修改后通过 / 需要修改]
```
